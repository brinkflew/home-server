# Scripts

**Which machine a script runs on is the first thing to know about it**, and `bin/` mixes both sides.
Each script says so in its own header; this is the table.

The split is not arbitrary. Anything holding a credential the server must not have runs on the
workstation, and anything that has to outlive the machine it is talking about cannot run on it.

| Script | Runs on | What it does |
|---|---|---|
| `backup-server.sh` | **server** | Backs up `config/` to `/var/backups/home-server`, then `restic copy` off-site with the append-only key. Nightly, from `home-server-backup.timer`. This is the backup that actually happens. |
| `snapshot-databases.sh` | **server** | Consistent SQLite snapshots through the backup API, found by magic bytes rather than extension. Called by the two backup scripts; little reason to run by hand. |
| `verify-host.sh` | **server** | The health battery, the MOTD, and `/var/lib/home-server/status.json`. Hourly, from `home-server-verify.timer`. `--json` prints the findings machine-readably; `--greenboot` drops every container check and emits no JSON. |
| `collect-metrics.py` | **server** | Every 30 seconds, the numbers no container can honestly measure here: host filesystems and network, the cgroup detail that separates a container holding cold page cache from a starved one, GPU encoder utilisation, sensors, SMART, `status.json` as series, and what the applications think is happening. Writes Prometheus exposition format into node-exporter's textfile directory rather than pushing, because Prometheus pulls. `--print` shows what it produces without writing; `--slow` forces the 5-minute tier; `--source <name>` runs one. Also writes the dashboard's two JSON documents - `activity.json` every 30s and `library.json` every 5 minutes - into `${DOCKER_VOLUME_CACHE}/dashboard/`, because titles cannot be Prometheus labels. |
| `storage-census.sh` | **server** | Breaks `/var` down by consumer once an hour, from `home-server-storage-census.timer`, into a marker `bin/verify-host.sh` and `bin/collect-metrics.py` both read. `node_filesystem_avail_bytes` says /var went from 47.4 GiB used to 146.4 GiB in 25 days and CANNOT say why; answering that took an ssh session and six `du`s. **`podman unshare du -x`, and the `-x` is load-bearing in the direction the repository had not recorded**: unsharing is right for a subuid-owned tree and a 78% OVER-read on the podman graph root, where `du` descends into every running container's `overlay/<id>/merged` and counts its whole rootfs on top of the layers it is made of. **It sums to `df` by construction**, publishing whatever no consumer claims as `other_unaccounted` - 1.3% measured - so a consumer nobody added shows up as that growing rather than as every share silently being wrong. One traversal per root at 7-9s total, which is why it is an hourly timer and not a collector source. `--dry-run` prints the breakdown and writes nothing. |
| `ci-artifacts-sweep.sh` | **server** | Sweeps the lanes' shared store daily from `home-server-ci-artifacts-sweep.timer` on **two windows**, and **never touches `state/`** - a few hundred bytes of coverage baseline whose loss makes upskald's gate PASS on every surface at once. `CI_ARTIFACT_KEEP_DAYS` is **30**, refuses below 7, and takes whole runs; `CI_ARTIFACT_NYC_KEEP_DAYS` is **3**, refuses below 2, and takes `*-nyc` artifact directories out of runs that are otherwise still current. **The split is the lever this file spent two revisions naming and not pulling**: measured 2026-09-11 over 106 run-attempts, `e2e-shard-N-nyc` was 53,638 MB of 53,659 - **99.96%** - so everything else is 472 MB for a fortnight of CI and thirty days of it costs about 1 GB. It was only takeable once the open question was answered: raw nyc has exactly one consumer, `e2e-and-coverage-report`, in the **same run**, minutes later - and the merge-time consumer that justified the seven-day floor reads GitHub artifacts, not this store. So whole-run granularity is kept for every class but nyc, which is the stated price. Writes its own marker; `ci.artifact_store` grades freshness and size. `--dry-run` says what it would remove. |
| `promote-transcoded.py` | **server** | Tells Radarr and Sonarr where Tdarr already moved a file. Every 10 minutes. Never moves media itself. |
| `search-missing.py` | **server** | Asks Sonarr and Radarr to search AGAIN for what is missing. Daily, from `home-server-search.timer`. Both applications search a title exactly once, when it is added, and RSS sync afterwards only sees what an indexer published recently - so nothing ever looks for a 2012 film or a series that ended in 2004 a second time. It refuses to search what is not released yet (16 of 21 wanted films were `announced`), what is already in the queue, anything it searched inside a week, or more than two dozen items a run - an item being one film or one EPISODE, since searching by season asks for a season pack and returned nothing. It queues search commands and nothing else, and it NAMES a stalled download rather than clearing one. `--dry-run` says what it would ask for. |
| `reboot-when-staged.sh` | **server** | The UNattended reboot, hourly 05:00-09:00 on Sundays from `home-server-reboot.timer`. Every check in it is a refusal - it applies a staged deployment only when greenboot is armed to undo it, nothing has been rejected and left unexplained, no backup is running, the host is healthy now, nobody is watching Jellyfin and no transcode is running. Three of those give way rather than refusing for ever: the transcode past 14 days staged or 30 days of uptime, and a phase or a viewer after the second refusal of a morning - the cheap interruptions are counted per morning, the expensive one is measured in days. **The playback gate is not redundant with the encoder gate**: a DirectPlay session opens no encode session, so `nvidia-smi` reads 0% while a film is playing. `--dry-run` says what it would do; `HOME_SERVER_STATUS_JSON`, `HOME_SERVER_STAGED_AGE_DAYS`, `HOME_SERVER_ENCODER_PCT` and `HOME_SERVER_WATCHING` make the otherwise-unreachable gates testable. |
| `reclaim-boot-slot.sh` | **server** | The "after" the unattended reboot never had, from `home-server-boot-reclaim.timer` - five minutes past a boot, then every thirty. `/boot` holds exactly two 145.3 MiB slots and an update needs a third transiently, so `bin/reboot-host.sh` has always ended in `rpm-ostree cleanup -r`; `reboot-when-staged.sh` reboots and the process that would do that dies with the machine. It drops the rollback deployment - and nothing else - after a green greenboot verdict **from this boot**, having first pinned the outgoing commit with an ostree ref so what is given up is the `/boot` entry rather than the deployment. `df` runs before any D-Bus call, so the no-op path never wakes rpm-ostreed; every shape it cannot name is a refusal, because `cleanup -r` retains `[booted]` and on four deployments removes three. `--dry-run` says what it would do; `HOME_SERVER_BOOT_FREE_MB` (set-but-empty means unreadable), `HOME_SERVER_STATUS_JSON`, `HOME_SERVER_BOOT_STATE` and `HOME_SERVER_GRUBENV` make every refusal reachable. |
| `jellyfin-watching.sh` | **server** | How many people a Jellyfin restart would interrupt, as one number on stdout. A session counts when it has a `NowPlayingItem` **and** checked in within the last 300s - the first drops an idle client with the app merely open, the second drops one that vanished without saying so and would otherwise veto for ever. A paused stream counts: the position is saved, but somebody who paused for tea is still watching, and a check-in stays fresh while paused so `IsPaused` cannot tell the two apart anyway. **Exit 2 means UNKNOWN** - running but unaskable - which the two callers deliberately price differently; a container that is not running is 0, since there is no session to interrupt in one that is already down. `--verbose` breaks it down by playback method, and by nothing else: a record of who watched what is surveillance of the household. `HOME_SERVER_WATCHING` (a count, or `unknown`) makes both callers testable. |
| `update-when-idle.sh` | **server** | The `ExecCondition=` on `podman-auto-update.service`: does the nightly container update run tonight? It defers while somebody is watching Jellyfin, because on 2026-08-19 an update recreated Jellyfin at 00:20:30 mid-stream and two of three connected clients never came back. **Exit 1 is a refusal** - the one place this inverts `reboot-when-staged.sh`, where `refuse()` exits 0 - because `ExecCondition=` reads non-zero as "skip quietly" and leaves the unit NOT failed, so a deferral does not read as a fault. It gates the whole run because `podman auto-update` takes no filter, suppresses itself for 6h after an allowed run so the three nightly attempts do not update three times, and **gives way past 3 days** - the staleness filter drops clients that are gone, only the ceiling drops a tab left open all night. Unknown PROCEEDS here and refuses in the reboot gate, which is the same asymmetry priced two ways. `--dry-run` decides and writes nothing. |
| `github-runner.sh` | **server** | One CI lane: mint a single-use just-in-time runner identity on the `avanserv` organisation, run exactly one GitHub Actions job in a `podman run --rm` container under a transient scope in `app-ci.slice`, tear the registration down, repeat. Started per lane by `home-server-github-runner@<n>.service`. **The organisation PAT never enters the container** - it reaches `curl` on stdin, so it is not in argv either, and the container gets only the JIT configuration, which is good for one job. **The loop is here rather than in `Restart=`**, because a finished job is a process exit and letting systemd cycle it would count successful work against the start limit. So a non-zero exit always means something a restart cannot fix, and says which: 2 bad lane, 3 configuration, 4 missing image, 5 credential rejected, 6 bad runner group. **Every lane takes work unconditionally.** It used to hold every lane above the first while a conduct phase was in flight; that was removed on 2026-08-28, because at three lanes it was parking two of them for some 36-38% of a working day. Nothing sequences CI against the agent fleet now - the cgroup ceilings on `app-ci.slice` and `app-agents.slice` are the only bound, and that file says what to watch. `GITHUB_RUNNER_ROOT` and `HOME_SERVER_CI_STATE` make it testable off the real paths. |
| `github-runner-smoke.sh` | **server** | The gate between `localhost/home-server/github-runner:next` and `:latest`, run by `home-server-github-runner-build.service` between the build and the promotion. Two classes, like `conduct-runner-smoke.sh` - but its containment legs are deliberately NOT that script's. A CI lane's runner tree IS writable and a container socket IS present, because the runner writes its own credentials and a job needs somewhere to start `services:` containers; copying those legs across and deleting the two that no longer hold would leave a gate promising more than it checks. They are replaced by the negatives that are true here: the reachable socket is the NESTED one on the lane's own store, no `config/`, no `/mnt/media`, no `cache/conduct/`, and no `GITHUB_RUNNER_PAT` in `/proc/1/environ`. Its three most important legs prove the image can run CONTAINERS at all - a nested pull of an unqualified short name, a published port answering on `localhost`, and a service container reaching `healthy` rather than sitting at `starting` for ever. `GITHUB_RUNNER_IMAGE` points it at a candidate. |
| `probe-credentials.sh` | **server** | The three credentials nothing else here proves still authenticate, daily from `home-server-credential-probe.timer`. `agents.model_credential` and `agents.publish_configured` end their own PASS message saying so, deliberately - presence and freshness is all a read of the filesystem can establish - and `GANDI_BEARER_TOKEN` had never been exercised at all, because every certificate on this host is its first issuance. **The Gandi leg WRITES**, at a probe name nothing resolves, and removes it on a trap: a PAT that can list the zone and not change it authenticates perfectly and renews nothing. **The model leg treats only 401 as a rejection**, because this is a scoped OAuth token and one has already been measured answering 403 to an endpoint it was not entitled to - reading that as revoked would warn for ever about a working fleet. Every leg is independent so one broken credential cannot hide another, results are `ok`/`failed`/`skipped` because a network that could not be reached says nothing about a token, and exit is always 0 - the finding is in the marker. `--dry-run` decides and writes nothing; `--only gandi\|model\|publish` runs one leg and keeps the others' answers. |
| `verify-segmentation.sh` | **server** | Are the forbidden edges still forbidden? Weekly from `home-server-verify-segmentation.timer`. The ten-network split IS the security model and nothing proved it on a schedule - `net.segment_isolation` reads the `isolate=` option hourly, and this sends the packet. **By IP from a throwaway container on the source network, never by name**: a container has one address per network it joins, and the unit files look identical either way. **The exit code is the finding, not merely its sign** - 124 is a dropped packet and a blocked edge, 1 is ECONNREFUSED, which means the packet arrived and only the port was shut and is not isolation at all. **It carries a positive control and throws the run away without one**, because a missing image or a podman that cannot start a container makes every forbidden edge read "dropped" - the answer it is hoping for. Every probe container carries `io.home-server.ephemeral`, or the collector counts it as a service. `--dry-run` prints the edges and starts nothing. |
| `clear-red-boot.sh` | **server** | Acknowledges a rejected boot, and clears **both** arms of it: `red_boot_at` in `boot-state`, which holds the unattended window, and `boot_counter` in `/boot/grub2/grubenv`, which is what actually decides whether GRUB boots the default or the fallback. Only a green boot clears the second, so it survives every repair in between - clearing only the first left a machine that looked acknowledged and still rolled back on its next reboot. Refuses when nothing is armed; `--dry-run` says what it would clear. |
| `render-env.sh` | **server** | Renders `.env` from `secrets/env.sops.env`. Also runnable on the workstation. |
| `render-template.py` | **server** | Substitutes `${VAR}` from `.env` into a tracked config template, atomically and 0600. From an `ExecStartPre=` on `ntfy`, `alertmanager` and `ntfy-alertmanager` - the three containers that read a config file and substitute nothing in it. It refuses on an unset variable rather than writing an empty one, because an empty password in a rendered config is not a startup failure, it is a service that authenticates nobody. `--check` names the variables a template needs. |
| `render-jellyfin-branding.py` | **server** | Puts `apps/jellyfin/custom.css` into Jellyfin's `branding.xml`. From an `ExecStartPre=` on `jellyfin.container`. |
| `render-jellyfin-encoding.py` | **server** | Puts `apps/jellyfin/encoding.conf` into Jellyfin's `encoding.xml`, one named element at a time. Never creates the document. From a second `ExecStartPre=` on `jellyfin.container`. |
| `verify-media.sh` | **server** | Does a library file's keyframe grid survive Jellyfin's HLS stream-copy path? Samples three 120s windows and FAILS on any keyframe interval below the 6s segment length, which is the condition that makes browser playback drift. `--library` sweeps, `--full` scans one file exhaustively. **Weekly from `home-server-verify-media.timer` since 2026-09-09** - it existed for weeks with no unit referencing it, on a population Tdarr adds to every day. `--gate` is the `ExecCondition=` half: it defers while somebody is watching, because the spindle loses 45% of its throughput to two readers, and unknown PROCEEDS since this is a read that costs nothing to interrupt. `--marker` writes the durable record `media.keyframe_drift` grades - which exists because **`exit 1` means two opposite things here**, a completed sweep that found drift and a `die()` that could not run at all, and a reader with only the exit code cannot tell the library being bad from the check being broken. |
| `backup-config.sh` | **workstation** | Pulls `config/` into `~/backups/home-server`. The third copy: different machine, different password. Not load-bearing for freshness any more. |
| `backup-offsite.sh` | **workstation** | Copies to Scaleway with the **admin** key, and prunes. The server cannot do this and must not be able to. |
| `verify-restore.sh` | **workstation** | Restores the latest snapshot to a scratch directory and asserts what came out. A backup is not proven until this passes. |
| `reboot-host.sh` | **workstation** | The attended reboot. On the workstation because the waiting cannot happen on the machine that is rebooting. |
| `remote-kexec.sh` | **workstation** | Boots the server into a live Fedora CoreOS in RAM. Touches no disk. |
| `remote-install.sh` | **workstation** | Writes uCore over `nvme0n1`. Irreversible. See `host/RUNBOOK.md` before running it. |
| `lint-repo.sh` | **either** | ASCII, executable bits, shellcheck, quadlet dry-run. |

**`lint-repo.sh` needs `shellcheck`, and SKIPS rather than FAILS without it** - so a machine that
does not have it reports `all checks passed` having never looked at a line of shell. That is
deliberate, because the script has to stay runnable on the server, where `/usr` is read-only. It
also means the workstation is the only place the check really happens, and it went unnoticed there
until 2026-08-14: the leg had never run at all. Install it the same way as `sops` and `age`, as a
static binary in `~/.local/bin`:

```bash
curl -sfL https://github.com/koalaman/shellcheck/releases/download/v0.10.0/shellcheck-v0.10.0.linux.x86_64.tar.xz \
  | tar -xJ -C /tmp && install -m 755 /tmp/shellcheck-v0.10.0/shellcheck ~/.local/bin/
```

**Two credentials never cross the boundary**, and that is the point of the split:

- The **admin** Scaleway key and the workstation's restic passwords stay on the workstation. They
  are what can delete backups, so putting them on the server would undo the reason the server's own
  key is append-only.
- The server's own age private key decrypts `secrets/`, so it holds the **append-only** key and the
  repository passwords - enough to write a backup and read one, never enough to destroy history.

## Deploying the metrics change of 2026-08-17 needs one manual run

`home_server_jellyfin_sessions` moved from the 5-minute tier to the 30-second one, so it moved from
`home-server-slow.prom` to `home-server.prom`. node-exporter concatenates every `*.prom`, and the
slow file is deliberately left alone on a fast-only tick - so on the first run after a `git pull`
the new fast file and the *previous* slow file both carry that metric with the same labels, which is
a genuine duplicate and fails the whole textfile scrape until the slow tier next runs.

It heals itself within five minutes. To skip the gap entirely, force one full run after pulling:

```bash
./bin/collect-metrics.py --slow          # rewrites BOTH files with the new layout
podman exec prometheus wget -q -O - \
  'http://127.0.0.1:9090/api/v1/query?query=node_textfile_scrape_error'   # expect 0
```
